# 0003. In-house auth: JWT access tokens, rotating refresh tokens, roles and audit log

- Status: Accepted
- Date: 2026-11-26

## Context

All four products need the same things:
- user login;
- tenant isolation, because every product is multi-tenant;
- three roles (admin, analyst, viewer) plus a platform-level superadmin;
- an audit trail of security-relevant actions.

The portfolio has to run locally and in CI without external accounts, and it should
show the security mechanics rather than hide them behind a vendor console. Later it
must still be able to move to a managed identity provider.

Options considered:

1. **A managed IdP** (Auth0, Amazon Cognito, Entra ID): hosted login, MFA, social
   login, standards-compliant OIDC.
2. **A self-hosted IdP** (Keycloak): full OIDC, but another service to run and configure.
3. **An in-house package** on FastAPI, PyJWT and pwdlib, with users and audit stored
   in our Postgres.

## Decision

Option 3, packaged as `core/auth` (`ai_platform_auth`) and mounted by every product
with `Auth.install(app)`.

- **Access tokens:** HS256 JWT, valid 15 minutes, with claims `sub`, `tenant_id`,
  `role`, `jti`, `iat` and `exp`.
  - They're stateless to verify. `get_current_user` still reloads the user on each
    request, so deactivation and role changes apply immediately.
  - The secret comes only from `JWT_SECRET`, which must be at least 32 bytes; the app
    won't start without it.
- **Refresh tokens:**
  - Opaque random values, stored as SHA-256 hashes and valid 7 days.
  - **Rotated on every use.** Tokens from one login share a `family_id`.
  - Presenting an already-rotated token is treated as theft, and the whole family is
    revoked. This follows OAuth 2.0 Security BCP refresh-token rotation.
- **Passwords:** Argon2id, 12–128 characters. Lockout after 5 failures for 15 minutes.
  - Every login failure returns one generic error.
  - Per-IP login rate limiting sits behind a `RateLimiter` interface.
- **Tenancy:** a `TenantScope` built from the verified token. Query helpers take it as
  an argument, and other tenants' rows return 404.
- **Audit:** an append-only `audit_log` table. The code has insert functions only, and
  a Postgres trigger blocks `UPDATE`, `DELETE` and `TRUNCATE`. Middleware audits every
  write request that no endpoint audited explicitly.
- **Storage:** everything lives in a dedicated Postgres schema, `auth`, with its own
  Alembic version table.

## Why not a managed IdP (for now)

- **Zero external dependencies:** `docker compose up` plus `pytest` exercises the whole
  flow, including in CI, with no tenant to register and no secrets to share.
- **The security logic is visible and tested:** lockout, rotation, reuse detection,
  tenant isolation and audit immutability.
- **Cost and setup time** fit a portfolio project.

## Trade-offs

- **We own security-sensitive code.** Mitigations:
  - well-known libraries (PyJWT, pwdlib/argon2-cffi);
  - strict JWT decoding (algorithm allow-list, required claims);
  - extensive tests.

  It still needs the scrutiny a vendor would get from its own security team.
- **Missing compared with a managed IdP:** MFA, SSO/OIDC federation, password reset by
  email, account recovery, bot protection and breached-password checks. Any of these
  becomes a requirement as soon as real users arrive.
- **HS256 means one shared secret.** Every service that verifies tokens can also mint
  them. If services owned by other teams need to verify tokens, move to RS256 or
  ES256 with a JWKS endpoint (or a managed IdP).
- **Access tokens can't be revoked before they expire.** That window is at most
  15 minutes. Reloading the user per request covers deactivation; a `jti` denylist
  would cover per-token revocation if needed.
- **The rate limiter is in-memory**, so limits apply per process. Use Redis behind
  the same interface once there are several instances.
- **The audit trigger protects against the application, not against a DB owner.**
  Production must run the app as a role with only `INSERT, SELECT` on `audit_log`.

## How to swap to Cognito (or another OIDC IdP) later

The products depend only on these, never on how tokens are issued:
- `auth.get_current_user`, `require_role`, `require_superadmin`, `get_tenant_scope`;
- `TenantScope`;
- the `audit()` helper.

To swap:
1. **Verify Cognito tokens.** Replace `decode_access_token` with a verifier for
   Cognito's RS256 ID or access tokens: fetch the JWKS, check `iss`, `aud`/`client_id`
   and `token_use`. Map claims: `sub` → user, a `custom:tenant_id` attribute → tenant,
   and a Cognito group (`admin` / `analyst` / `viewer`) → role.
2. **Keep the `users` table** as a local profile keyed by the Cognito `sub`. Add a
   `external_subject` column, and drop `password_hash`, `failed_logins` and
   `locked_until` once Cognito owns credentials. Tenant and role checks keep working.
3. **Remove the password endpoints.** `/auth/login`, `/refresh` and `/logout` go away;
   use Cognito Hosted UI or SDK flows with PKCE. Cognito then handles lockout, MFA
   and refresh-token rotation.
4. **Keep the audit log.** Write login events from Cognito triggers (or the
   CloudTrail/EventBridge feed) and keep the middleware for writes.

The tenant-isolation and role tests stay valid; only the tests for token issuance and
password handling are replaced.

## Consequences

- Every product gets the same login, roles, tenant model and audit trail by adding one
  dependency and calling `Auth.install`.
- CI now needs a Postgres service container, and database tests can't be skipped there
  (`REQUIRE_DB_TESTS=1`).
- `ai_platform_common` gains SQLAlchemy, Alembic and psycopg as dependencies, for the
  shared DB helpers.
