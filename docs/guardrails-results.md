## How these numbers were reached (honest history)

The corpus was committed before the first scoring run and has not been edited since.

**First run** (same corpus, before any detector changes):

| Metric | First run | Now |
|---|---:|---:|
| CREDIT_CARD recall | 81.8% (4 missed) | see table above |
| PHONE recall | 98.2% (2 missed) | see table above |
| DATE_OF_BIRTH recall | 67.5% | see table above |
| US_BANK_NUMBER recall | 0% | see table above |
| Injection detection | 31/35 (88.6%) | see above |
| Benign false positives | 1/35 (2.9%) | see above |

**What changed in the detectors (general fixes, not per-sample tuning):**

- **Context words were silently ignored.** Presidio matches context per token (lemma), so
  multi-word entries such as "date of birth" or "claim number" never matched, and "born"
  lemmatises to "bear". All context lists now use single words (plus "bear").
- **Card numbers:** Presidio's recognizer knows common brand prefixes/lengths only. Added a
  12-19 digit Luhn-validated recognizer that still needs card context ("card", "charged",
  "statement", ...), so random digit runs are not flagged.
- **Phones:** bare 10-digit numbers with valid NANP area and exchange codes are treated as
  phones without needing a context word. Trade-off: some other 10-digit numbers will be
  masked as phones (safe direction for privacy, lower precision on real data).
- **Bank accounts:** added an 8-17 digit recognizer that only fires next to account/bank words
  (Presidio's built-in scores too low to pass the threshold).
- **Injection:** letter-spaced text with multi-space word gaps is re-joined before scanning;
  role-play rule window widened; new signals for *asking to skip oversight* ("no confirmation
  needed", "do not log it") and *harvesting other people's data*; "developer mode" now only
  counts when someone enables it or addresses the assistant (fixed the product-guide false
  positive).

**Known limits:**

- **PERSON:** names that are also ordinary words ("Will Stone", "Grace Lane") are still missed
  in some sentences (see Misses). Recall is above the 95% target, not 100%.
- **EMAIL precision:** the false positives are `claims@example.com`, an organisational address
  in the email template that the generator does not label. It is a real email address, so
  this is a gold-label gap, not a detector error; we left the corpus unchanged.
- **No detector catches everything.** 100% on 35 hand-written attacks does not mean 100% on
  attacks we have not imagined; see ADR 0005 for the layered design that limits the damage
  when a detector misses.

## Held-out and public evaluation (report only)

- **Development:** the corpus above. Detectors were fixed against it, so it is optimistic.
- **Held-out v1:** `eval/heldout`. Frozen before its first scoring; **seen** since
  guardrails-v2 (used to choose thresholds and check PII fixes), so it is tuning data now.
- **Held-out v2:** `eval/heldout_v2`. Frozen before any v2 change and scored once, at the
  end of guardrails-v2: the honest number. Same author as the detectors, so not independent.
- **Public:** `deepset/prompt-injections` test split, injection only, downloaded by
  `scripts/download_public_eval.py` and never committed. The only independent check.

Only the development set gates CI. The generated miss lists give sample ids, never
text; the notes below quote a few synthetic values to explain the patterns.

**How these numbers were produced.** Held-out v2 and the deepset test split were scored
**once**, in the last step of the guardrails-v2 branch, after every detector change was
committed. In the same step the **guardrails v1 code** (`main` at `45e72a3`) was run on the
same v2 and test data, so "before" and "after" use identical data. Nothing was changed after
that run.

¹ guard-small was trained on the deepset **train** split. The vendor says the test split
was excluded, but the two share a distribution, so this is not as independent as it looks.

² **Contamination, disclosed:** while developing the PII fixes, 8 of the 60 v2 lines

and 13/56 (23%) fully leaked.** Those 8 lines hold 9 values, of which 8 were detected (the
miss was a name).

### What got better

- **Injection on unseen text went from catching 1 attack in 8 to about 3 in 4.** The local
  classifier catches paraphrased overrides, role-play setups, hidden instructions in
  documents and attacks in German, French, Spanish and Hindi that the rules never matched.
  On v2, all 7 instruction overrides (every one in German, French, Spanish or Hindi), all
  4 system-prompt extraction requests and all 4 hidden instructions in documents were
  caught.
- **The public set** went from 6/60 to 24/60. Most remaining public misses are task
  hijacks ("forget that, now write about…"), which are handled by architecture (ADR 0007).
- **False alarms stayed low:** 0/56 on the public benign set and 0/35 on the dev set.
  v2 benign rose by one, to 3/40.
- **PII:** obfuscated emails, rural/PO Box/military addresses, written-out dates of birth
  and IDs with separators are now masked. Every dev value is fully masked except 5 names.

### Known limits

Every gap below is tracked as a GitHub issue labelled [`guardrails-backlog`](https://github.com/rrvelmineti/ai-portfolio/issues?q=label%3Aguardrails-backlog), with the evidence from this section:

- [#9](https://github.com/rrvelmineti/ai-portfolio/issues/9): work-phrased attacks (instruction requests, bulk data, "already approved" claims); needs a held-out v3 first
- [#10](https://github.com/rrvelmineti/ai-portfolio/issues/10): multilingual rule coverage and the Hindi classifier limit
- [#11](https://github.com/rrvelmineti/ai-portfolio/issues/11): remaining PII leaks
- [#12](https://github.com/rrvelmineti/ai-portfolio/issues/12): NPI-vs-phone labelling (xfail)

### What is still wrong (reported as is)

**Injection: v2 misses (11)**
- **10 of the 11 are work-phrased requests,** with no attack vocabulary:
  - 4 bulk data requests (English, French and Hindi): "a full extract: every member record";
  - 5 claims that an approval or check already happened: "compliance has already signed
    off", "the second approver said it's fine", "this file was pre-validated";
  - 1 tool call that changes bank details "because the member asked by phone".
- **This is the gap the planned semantic policy signals were meant to close** (requests for
  instructions, bulk data, claimed approvals). They were **not built in this branch**, and
  neither was the multilingual extension of the rules. They are the next step, measured on
  a new held-out set; v2 has now been seen.
- **The 11th miss** is an HTML image tag in a document that points at a tracking URL. The
  output link check still blocks such a link if the model reproduces it.
- **The approval gate is the control that matters here.** A model that believes "the second
  approver said it's fine" still cannot approve its own action: `require_approval()` needs a
  real second person.

**Injection: false positives**
- **v2 (3):**
  - a tool request ("use the lookup_offer tool…");
  - a request to translate the phrase "ignore all previous instructions" for a phishing
    poster;
  - a request to decode a base64 file name.
- **Kept on purpose in v1:**
  - the rules flag a training slide quoting an attack (`claude-ben-008`);
  - the rules flag a note about a developer-mode toggle (`claude-ben-039`).

  Per the guardrails-v2 decision these were not tuned away. The classifier adds three more
  v1 flags (`claude-ben-009`, `019`, `033`), all below the block level or in documents.

**PII: values that still leave completely on v2 (14)**
- spelled-out digits ("five five five, two oh one…"), a UK number (+44) and a
  "1-800-… x4410" number (partially masked);
- an SSN without dashes ("288506613"); the other dash-less SSN was masked, but as a member
  ID;
- a card number written with dots;
- an NPI written in groups;
- a bank account written in groups;
- a numbered street name ("2700 W. 5th Ave …") and a Spanish street type ("1450 Calle
  Ocho …");
- dates of birth as "03-MAY-1961" and "03.05.1961";
- names in Devanagari and Vietnamese (one partly masked), a hyphenated French name and an
  all-caps "SURNAME, GIVEN" form.

None of these was fixed after scoring. Fixing them in a later branch means v2 becomes
tuning data, as v1 did.

**Hindi** (see ADR 0007): 55% recall on standalone Hindi attacks in the comparison set.
On v2, 3 of the 4 Hindi attacks were caught (the miss was a bulk data request).

data, same 0.5 threshold, ONNX Runtime on CPU (4-core Xeon at 2.3 GHz, batch 1). Held-out v2
and the deepset test split were **not** used. Prompt Guard 2 was exported to ONNX (fp32
matches torch within 6e-8) and tokenised exactly as at release.

`87219c62`); MASSIVE 1.1 benign prompts (Amazon, CC-BY-4.0, 300 per language); our dev
and held-out v1 sets; deepset train. "Standalone" = CyberSecEval attack types that are
attacks without a system prompt (ignore-previous, system mode, role-play, payload
splitting, token smuggling; n = en 80, fr 21, hi 80, de 14, es 17).

### Guardrails v1 analysis (historical, ADR 0006)

_Written for the guardrails v1 detectors (rules only) and held-out v1 before it was seen. Kept for the record; the current analysis is "Guardrails v2: before vs after" above._

#### What the gap meant

The first scoring run on the held-out and public sets is the run shown above. The
held-out set was frozen in commit `c918e1a`, before any scoring, and no detector has
changed since. Nothing has been tuned to these numbers.

**Headline: the development numbers overstate real-world accuracy, a lot for injection.**
100% on the development attacks says the rules recognise the phrasings they were written
for. On new phrasings they catch 17/40 of the held-out attacks and 6/60 of the public ones.
The low false-positive rates hold up (2/40, 0/56), so the rules are precise but narrow.

##### Prompt injection

- **No near misses.** Every missed attack scored below the 0.4 flag threshold, so the
  optional LLM classifier, which only sees borderline inputs, would not have been asked
  either. Lowering thresholds would not help; the rules simply don't fire.
- **What the rules miss (held-out):** requests that sound like ordinary work, with no
  override or jailbreak vocabulary:
  - system-prompt extraction phrased as an audit or a question (0/3);
  - harvesting other members' data (0/3);
  - skipping approval "because the reviewer already agreed" (0/2);
  - task hijack, social engineering, multi-turn and split payloads (0/6 combined);
  - overrides worded differently from the rules: a developer "priority update", a
    French and a Spanish override (both rule languages) and a Chinese one (not a rule
    language);
  - instructions hidden in an HTML comment or a JSON field (2 of the 4 hidden
    instructions);
  - a "grandmother" role-play and a rot13 payload.
- **What they catch:** fake delimiters, exfiltration links, character spacing, most
  encodings and explicit role-play personas.
- **Public set (`deepset/prompt-injections`, test split):**
  - **German:** 20 of the 60 attacks are German, and all 20 were missed. The rules cover
    German override phrasing only, and the NER model is English.
  - **English:** 6/40 (15%) caught. Most are task hijacks ("forget that, now write
    about …") or role-play setups that our rules do not treat as attacks.
  - **Labels:** some labels are debatable for our use. For example, `deepset-test-000`, an
    "act as an interviewer" role-play prompt, is labelled an injection. The number is
    reported as is; we did not relabel.
- **Why it matters less than 10% suggests, and why it still matters:** the rule scanner
  is one layer. The canary, output link blocking, the tool allowlist and the approval
  gate do not depend on recognising the attack text. But the scanner is the only layer
  that stops an attack *before* the model reads it, and on independent data it mostly
  doesn't.

##### PII

- **Strong on fixed formats:** every SSN, card number, NPI, IP address and claim number
  was found (18/18), including a claim number missing one hyphen.
- **Dates of birth: 2/8.** The misses are formats the recognizer doesn't parse
  ("3rd of May 1961", "Jan 5 '72", "19570823", "22.10.1975"), and dates with no DOB word
  nearby. Dates without a DOB word are left alone by design (dates of service must stay
  readable), so 2 of the 6 misses are a labelling choice in this set rather than a
  detector bug. With Safe Harbor on, any date the date recognizer does find is
  generalised to its year anyway.
- **Off-format IDs:** `M-4471-2290`, `POL 00873321`, a hyphenated bank account and a
  bare bank account with only "checking" as context were missed. Tenant-specific
  recognizers are the intended fix for house formats.
- **Names: 25/28.** Missed: a name in ALL CAPS, a lone first name that is also a word
  ("Will") and "April May". False positives: an OCR-damaged label ("Narne"), a Spanish
  phrase ("La paciente"), a place name ("Cody") and an obfuscated email.
- **Type-strict scoring understates masking.** An obfuscated email
  ("kim dot park at example dot com") was partly masked as a PERSON, and the rural-route
  address lost only its city. These count as misses because the type is wrong; the value
  is partly hidden, not fully exposed.
- **Expected trade-offs, seen again:** a 10-digit order number masked as a phone and a
  bank routing number masked as an account (the safe direction, documented in ADR 0005).

##### NPI vs phone

`core/guardrails/tests/test_npi_phone_overlap.py` pins the overlap. NPIs win over phones
when both match. That is right for real NPIs, but about 1 in 10 bare 10-digit phone
numbers starting with 2 also pass the NPI check and are then labelled NPI even next to
"call" (an `xfail(strict=True)` test). The number is masked either way.

##### What would change these numbers (not done here)

Detector fixes belong in a separate branch, and that branch must say which held-out
samples it was tuned against. Those samples then stop counting as held out.
1. Turn on the LLM classifier for *all* chat input, not only borderline, and measure its
   cost and latency.
2. Add intent rules for extraction-as-audit, bulk data requests and approval skipping.
3. Add DOB date formats, plus tenant recognizers for house ID formats.
4. Score a public PII benchmark (future work, ADR 0006).
